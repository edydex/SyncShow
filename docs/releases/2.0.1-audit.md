# SyncShow 2.0.1 release audit

Audited October 4, 2026, for the Prepare → Load → Show church workflow. The audit uses isolated profiles and source worktrees; existing primary checkouts and real service drafts are preserved. The Community server is not deployed by this release.

## Confirmed issues and corrections

| Issue | Correction and regression evidence |
| --- | --- |
| Adjust sometimes reset to the first slide during its cold mount. | Avoid a duplicate automatic service-open transaction. The native rehearsal opens the bundled editor from a cold, offline state and follows slide 20, slide 88, then slide 20 again. |
| A take finishing while Adjust opened could leave its selected slide stale. | Resolve selection against the latest installed cue graph and wait for the collapsed section to render before scrolling. |
| Reopening after the Stage-Facing Screen left the user on a read-only output. | Restore an editable audience output while retaining English/Russian audience choices. |
| Editing a repeated song section, or materializing song pages for move/delete, could replace unrelated cue identities. | Retain bounded occurrence and single-page source identities. Test ordinary corrections, independent chorus repetitions, moves, confirmed deletions, duplicates, output language choices, per-slide formatting and Next navigation. Copies receive fresh identities; duplicate compiled cue identities are rejected. |
| Add-slide song/media lists could remain stale after an online update. | Revalidate mutable libraries with a bounded wait and retain the local/Prepare cache when offline. Mutations also refresh cached lists. |
| Background song prefetch and an explicit library read could race a partially rewritten response cache. | Publish metadata and payload together as one atomic response record. Retain readable older cache records; treat damaged or incomplete records as cache misses so available fallbacks can recover. |
| An earlier slow prefetch could overwrite a newer offline song or sermon copy. | Assign generations before the fetch and retain the newest successfully committed response. Failed newer requests do not discard an earlier usable response, and malformed JSON does not replace a valid cache. |
| Native service readiness could be overwritten by a background Legacy PPTX/Google Drive error. | Restrict legacy scans to their selected mode and invalidate late callbacks after switching to native services. |
| Leaving Community Prepare after choosing Legacy PPTX could send Load to the wrong source mode. | Make the return to native service Load explicit, including pending-save and failed-save paths. |
| Offline writes needed stronger completion guarantees, especially on Windows. | Flush the published file as well as the rename operation. Exercise local save, restart, history, conflicts and queued synchronization. |
| Packaging could carry stale editor helpers or provenance. | Bind the built editor, font, three retained TypeScript source snapshots and actual shared service core to exact bytes and SHA-256 fingerprints. |
| Official Gitiles source archives changed request timestamps between downloads. | Normalize archive metadata while preserving exact file content, modes and links. Verify immutable revisions and pinned canonical hashes; reject changed or unsafe source contents. |
| The CI packager tried to publish installers before the final verification stage. | Disable packager publishing explicitly on every build target and give publishing authority only to the final checked release job. |
| A version bump earlier in a multi-commit push could be missed by the automatic release trigger. | Compare against the branch state before the entire push. Exercise actual workflow shell steps with temporary Git histories, including manual, initial and unchanged pushes. |

## Verification and its limits

The final local JavaScript and regression gate completed with 2,536 passing tests, two skipped and no failures. Independent focused reviews covered structural song identities, atomic cache replacement and release publication contracts.

Three consecutive cold-start native Mac rehearsals passed with the actual shared bundled editor, a 101-cue bilingual service, cached image media and three real Electron output windows. Local saves took 175–186 ms and slide takes 113–118 ms in those runs. The display inventory is synthetic so the test cannot hijack real screens. The rehearsal tests backstage saves and thumbnail refresh, stable audience output until a take, repeated chorus corrections, structural edits and subsequent navigation. It makes no service-document reads during Adjust. This is native app evidence, not a claim of three physical projectors.

Each public release build runs the broad regression suite on Windows, Linux, Apple Silicon Mac and Intel Mac. Each target then checks the packaged PDF renderer, Sharp native image library, shared service core, legal/source materials and isolated packaged-app launch. Windows additionally installs the exact NSIS installer on a disposable runner, compares its installed executable and application archive to the checked package, launches the installed app in an isolated profile, and uninstalls it. The final publication gate binds all installers and receipts to the same version and source revision and produces SHA256SUMS.

Mac physical output testing and the release download checks are recorded separately from the automated rehearsal. The church's Windows projector, sound routing and operator handoff still need an on-site rehearsal. Legacy PowerPoint conversion requires the documented external converter and is separate from native SyncShow services.

An independent code review checked structural song identities and a language/title/media edge matrix. A paid Muse API consultation supplied additional operator scenarios; its suggestions were treated as review prompts, not proof that the software passed them.

## Compatibility

An older Community server may reject the new per-occurrence identities used by independently edited or structurally moved song pages. The app keeps the exact edit, history and show package locally with synchronization pending; it does not strip identities or overwrite the server with a changed interpretation. Ordinary service use remains available. Updating that server's compatible service core is a separate deployment.

Mac packages have ad-hoc signatures, not Developer ID signatures or notarization. Windows installers are not Authenticode signed. The release checks do not claim otherwise.
