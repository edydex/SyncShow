### Acknowledged all-output live cue navigation — August 10–11, 2026

**During an active visible Show, SyncShow now changes its authoritative current
cue only after every exact routed output has acknowledged the matching rendered
frame.** Main snapshots the output session, output IDs, and sender identities,
arms every expectation before the first renderer send, rejects overlapping
navigation, validates the final all-output receipt against current state, and
only then commits the cue. Local controls and Remote Next, Previous, and jump
use this same confirmed path.

While a transition is pending, Show exposes **Changing cue…** and disables
further navigation, Restore, and Bible presentation. Held keys, rapid double
Next, and a competing Remote command cannot dispatch another cue. Singer image
success now waits for decode, DOM replacement, and two paint frames. Bible
lookup also acquires its pending token before asynchronous resolution, so Bible
and cue navigation cannot cross in either ordering.

A negative renderer acknowledgement or dispatch failure retains the previous
**authoritative cue index** and requests Clear. A timeout or unresponsive output
also keeps that index, hides the output windows, and stops the affected output
session rather than claiming a successful black frame. Because a renderer
paints before it acknowledges, this does not claim that the prior cue stayed on
every audience screen during the 15-second deadline. Clear, Stop, and
output-session replacement cancel a pending transition without allowing a late
receipt to commit it. The transition timeout is 15 seconds; the browser Remote
command timeout is longer at 20 seconds.

Restore now closes the corresponding recovery hazard without exposing the
desktop after Clear. Each exact renderer first paints and acknowledges an
opaque full-viewport black guard. An output that was already showing Clear is
never hidden or re-fullscreened; a stopped output is shown only after its black
guard is proven. SyncShow then re-sends the authoritative current cue beneath
the guards, waits for a same-cue sender/session-bound receipt from every routed
output, and performs an all-output release-readiness phase before revealing.
A timed-out renderer can therefore hold an uncommitted newer cue in its DOM
without flashing that cue when the operator restores the Show. Multi-output
guard release is acknowledged but not an atomic two-phase reveal: for a brief
interval, a screen can be either black or already showing the same
authoritative cue.

## Product workflows that must stay intact

### 1. Native Prepare workflow

Native services render constrained live HTML/CSS scenes in output windows.
Operator thumbnails are rasterized; the live native output is not a folder of
full-size slide images.

Implemented foundations include:

- Markdown/TXT SongDocuments with `^X` sections and explicit slide breaks
- searchable, revisioned local song library
- original/translation relationships and per-output variants
- atomic in-place replacement of a retained planned song
- song intro cards with exact or structured credits
- hierarchical service/sermon groups
- canonical-sermon-body review into editable native cues, with explicit
  per-output entry/Hidden choices and rows that begin at Skip
- sermon/notice text with per-output titles and bounded gold emphasis
- blank and per-output picture cues
- arrangements, repeat sections, nesting, reorder, duplicate, undo/redo
- pinned BSB/LSV Bible passages with Heritage-style shorthand and ambiguity
- portable `.syncshow-service` import/export
- immutable native ShowPackages with scene checksums and equal output lengths

The July 19 service was recreated as a 114-cue native project using reviewed
source decks; other dates primarily contributed song-library content. Do not
assume every historical service has a complete native sermon/project. The next
proof must be an ordinary current weekly service authored in SyncShow, restarted
into Load, rehearsed, and run by a volunteer on venue hardware.

### 2. Friendly operator workflow

The intended flow is:

`Prepare → Load → Show`

`Load` opens by default.

Friendly Load should show only administrator-configured input cards such as
Russian, English, and Singers. Folder/Drive setup, screen mappings, output
definitions, role matchers, timing, preview choices, and Singer typography
belong behind **Admin Settings**, with the deliberate advanced-settings warning.

Do not re-clutter Friendly Load with implementation detail.

### 3. Legacy and emergency PPTX fallback

This path remains required during migration, for old services, and when native
preparation cannot be completed. It is compatibility, not the product model.

- Windows prefers installed Microsoft PowerPoint for legacy fidelity.
- If PowerPoint is already running, SyncShow must not close or interrupt it;
  use isolated LibreOffice fallback.
- If that fallback is unavailable or also fails, the exact role card keeps the
  prior deck safe and offers **I closed PowerPoint — retry**. The renderer
  reuses the exact approved file and restore binding; it never closes
  PowerPoint itself.
- macOS/Linux use LibreOffice.
- Imported PPT/PPTX remains source-faithful and pre-rendered to slide images.
- Conversion uses staged generations, validation, an active cache, and
  last-good rollback.
- Public/private Drive or a local folder can populate the configured input
  cards.
- A service is one coherent same-date set; never silently mix unrelated dates
  or decks.
- Missing Singer/Media offers: choose its deck, derive next-line content from a
  loaded deck, mirror a loaded deck, or disable that output for this service.

Keep this path regression-tested. Postpone further semantic PowerPoint
processing until the native weekly loop and volunteer venue rehearsal are
complete.

- macOS builds are ad-hoc signed and not notarized.
